## Project

Research code for "Motion Synthesis with Sparse and Flexible Keyjoint Control" (SFControl): a diffusion model over HumanML3D motion, trained in two stages. Stage 1 generates end-effector keyjoints; stage 2 generates full-body motion conditioned on them. Derived from CondMDI, GMD and MDM.

- The goal of this project is to retrain this model on LAFAN1 dataset located in /NAS/Personal/HaeminKim/06_Research/00_Data/Geno_Holden/LAFAN1_resolved/to_YBot. The train and validation splits are in /NAS/Personal/HaeminKim/06_Research/00_Data/Geno_Holden/LAFAN1_resolved/to_YBot/file_splits_no_obs.yaml
- Data format: Character: ybot_skin_mod.bvh, Motion: bvh files: ./bvh_total, npy files in [frames, joints, 4, 4]: ./npy_total, Frame rate: 60 FPS
- Train without text labels
- Lengths trained with: [30, 73, 115, 158, 200]

## Commands

Run from the repo root (paths like `save/` and `./dataset/` are relative to it), after `source /opt/conda/etc/profile.d/conda.sh && conda activate /host_source/van/envs/sfcontrol`.

LAFAN1 data (once) and checks (see `LAFAN_process/README.md`):
```bash
python -m LAFAN_process.preprocess_lafan
python -m LAFAN_process.check_lafan --out_dir save/lafan_check
```

Train stage 1 on LAFAN1 (saves to `save/lafan_stage1_glo_joints_random_joints/`):
```bash
python -m train.train_sfcontrol --endeffector_conditioned --endeffector_only --endeffector_selection_scheme random_joints --head --diffusion_steps 50 --latent_dim 128 --lambda_ric_pos 0.1 --lambda_ric_vel 10.0 --lambda_ric_fc 10.0 --dataset lafan --data_rep glo_joints --num_frames 224
```

Train stage 1 on HumanML3D (end-effector keyjoints):
```bash
python -m train.train_sfcontrol   --endeffector_conditioned   --endeffector_only   --endeffector_selection_scheme random_joints   --head   --diffusion_steps 50   --latent_dim 128   --lambda_ric_pos 0.1   --lambda_ric_vel 10.0   --lambda_ric_fc 10.0   --dataset humanml   --data_rep glo_joints
```

Train stage 2 (full body, conditioned on keyjoints; HumanML3D only):
```bash
python -m train.train_sfcontrol   --endeffector_conditioned   --endeffector_selection_scheme all_endeffectors   --head   --diffusion_steps 50   --latent_dim 512   --dataset humanml   --data_rep glo_root
```

There is no single-test command because there are no tests. To smoke-test a training change, add `--num_steps 300 --log_interval 50` (about 1 min for LAFAN1 stage 1 on the RTX 3090) and delete the save folder afterwards. `LAFAN_process/check_lafan.py` checks the LAFAN1 data path and the stage-1 loss positions.

Training writes losses to stdout, `<save_dir>/log.txt` and `<save_dir>/progress.csv` every `--log_interval` steps and stops after exactly `--num_steps` steps.

## Architecture

**Config composition.** `configs/` builds run configs by multiple inheritance of dataclasses: `data.py` (dataset/abs-3d/projection variants) and `model.py` (architecture variants) are mixed together in `card.py` (e.g. `motion_abs_unet_adagn_xl`). `utils/parser_util.py` defines the option dataclasses (`DataOptions`, `ModelOptions`, `DiffusionOptions`, `TrainingOptions`, `SamplingOptions`, …); `train_args(base_cls=...)` turns a card into argparse flags via `utils/hfargparse.py`. CLI flags override the card defaults. `train_sfcontrol.py` defaults to `card.motion_abs_unet_adagn_xl` when no card is given.

**Stage selection is derived from flags, not passed directly.** `train_sfcontrol.py` sets `save_dir = save/{prefix}_stage{1|2}_{data_rep}_{endeffector_selection_scheme}` based on `--endeffector_only`, where `prefix` is `t2m` for HumanML3D and the dataset name otherwise (e.g. `lafan`). Stage 1 with no conditioning forces the scheme to `none`. `args.json` is written into that directory. `utils/model_util.py:get_model_args` then switches the model shape on the same flags: stage 1 uses 16 joints (+3 with `--head`, +2 with `fc`); stage 2 uses 67 joints for `glo_joints`/`drop_redundant`, else 263. `keyframe_conditioned` and `keyframe_selection_scheme` are passed into the model from these flags.

**Model factory.** `utils/model_util.py:create_model_and_diffusion` dispatches on `--arch` prefix: `dit*` → `model/mdm_dit.py`, `unet*` → `model/mdm_unet.py`, otherwise → `model/mdm.py` (transformer encoder/decoder). `two_head` in the arch string means predict both eps and x0; UNet forbids it.

**Diffusion and conditioning.** `diffusion/gaussian_diffusion.py` holds the sampling and loss logic. Stage behavior is a two-phase schedule: sampling switches from stage 1 to stage 2 at a timestep controlled by `cond_until_second_stage` / `impute_until_second_stage` in `model_kwargs['y']`, and stage-1 foot-physics terms are applied only for the first 30 steps. Inference-time control is pluggable through two decorator-registered registries: `diffusion/condition_methods.py` (`@register_conditioning_method`, projection / manifold-gradient / posterior-sampling variants) and `diffusion/blending_methods.py` (`@register_blending_method`, e.g. `LinearBlending`) . Keyframe/inpainting masks come from `utils/editing_util.py`. Guidance losses (start, goal, collision SDF) live in `diffusion/guidance.py`.

**Generation templates.** `utils/generation_template.py:get_template` takes a name (`no`, `trajectory`, `kps`, `sdf`, `testing`, `mdm_legacy`) and mutates the generation args: `guidance_mode`, `do_inpaint`, `gen_two_stages`, `p2p_impute`, `use_ddim`. These are the switches that choose which control mode a sample run uses.

**Data.** `data_loaders/get_data.py` dispatches on `--dataset` (`humanml`, `kit`, `amass`, `uestc`, `humanact12`, `lafan`) and builds a `DatasetConfig` dataclass. HumanML3D loading is in `data_loaders/humanml/data/dataset.py`; `Text2MotionDatasetV2` handles the global representations (`glo_root`, `glo_joints`), absolute-3D inputs, random projections, and stage-1 inverse transforms (`inv_transform_stage1`). `data_loaders/tensors.py` provides the collate functions. Training code reads `data.dataset.t2m_dataset` (`inv_transform*`, `endeffector_joints`, optional `fps`), so a new dataset must expose those.

**LAFAN1 (`LAFAN_process/`).** YBot joints are reordered into the SMPL/HumanML3D joint order (identical tree), so every hard-coded HumanML3D joint index applies unchanged. `dataset_lafan.LAFAN1` stores world joint positions per long sequence and, for each item, cuts a random window (length from `LENGTHS`, 60 fps), converts it to `glo_joints` with `representation.window_to_glo_joints`, normalizes, pads and returns the same tuple as `Text2MotionDatasetV2` with empty text. No text means `cond_mode='no_cond'` automatically. Stage 2 is not implemented for LAFAN1.

**Data representation.** `--data_rep glo_joints` (stage 1, 67 joints after dropping redundant features) and `glo_root` (stage 2) must match between training and any later use of the checkpoint; `args.json` in the save dir is the record of what was used. In `glo_joints`, features 0-3 are `[heading, root x, root z, root y]` and the rest are already global joint positions: convert with `recover_from_glo_joints`, not `recover_from_ric` (which would transform them a second time). The `ric_*` losses switch on `DiffusionConfig.glo_joints` for this.

**Variable length.** Items are padded to `--num_frames` with a per-sample length; the collate builds `y['mask']`, all losses are masked, and keyframes are sampled within the length. The UNet always pads to a hard-coded 224 frames (`model/mdm_unet.py`), so `--num_frames` must be ≤ 224.

**Frame rate.** HumanML3D is 20 fps and several constants assume it. The training foot-contact threshold is rescaled from the dataset's `fps` in `train_sfcontrol.py`; sampling-time constants are not (see `docs/implementation_issues.md`).

**Checkpoints.** Written under `save/` (gitignored). `train/training_loop.py` also maintains an EMA "average model" and strips CLIP weights from checkpoints (`del_clip`); `utils/model_util.py:load_saved_model` and `load_model_wo_clip` handle loading back.

## Development Workflow (For Claude)
### Bug Discovery and Documentation Workflow

- **ALWAYS document implementation issues immediately when discovered during testing**
  - As soon as you discover something, document it in appropriate analysis files
  - Don't wait for user to ask for implementation issues
  - Create detailed analysis with severity, category, location, impact, and recommendations
  - After testing completion, user reviews the document to decide true positives vs false positives
  - Then fix true positives and update tests accordingly
  - This workflow ensures systematic issue tracking and prevents bugs from being forgotten

## Documentation Best Practices

- Follow Numpy-style docstrings for consistency

### Standard Documentation Sections (in order)

1. **Brief description** - What the function does (first paragraph)
2. **Detailed explanation (if relevant)** - How it works, algorithms used, performance characteristics
3. **Parameters**: Describe input parameters with types and default values if applicable
4. **Returns**: Describe return values with types
5. **Raises**: List exceptions that may be raised

- **Line Length Standard** : 79 characters maximum
If unsure of style consult existing code for examples.

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

After a subagent's work, do a review and fix the critical mistakes. Always report to me what was changed, and list the non-critical findings that were left as they are.

Do not run not any code that would take more than 30 minutes. Just tell me what to do if this happens
